# ONCache 论文源码盘点与 v0.5 组件映射

> 盘点范围：`/home/endpca/on-m/论文源码/`
> 盘点阶段：M0-1、M0-2
> 结论性质：只读源码审计，不代表源码已适配 v0.5

## 1. 目录与构建状态

源码仓库的主体目录如下：

| 目录 | 内容 |
|---|---|
| `tc_prog/` | 四个 TC/eBPF section，源码实际集中在一个 C 文件中 |
| `user_prog/` | TC 加载器、Map 初始化工具、Python daemon 和 Antrea 配置脚本 |
| `common/` | 共享 C/C++ 定义和 Make 变量 |
| `headers/` | 随仓库保存的 Linux/BPF/libbpf 头文件 |
| `rpeer_kernel_patch/` | 基于 Linux 5.14 的 `bpf_redirect_rpeer` 内核补丁 |
| `scripts/` | Kubernetes 实验环境和 netperf/iperf3 脚本 |
| `libbpf/`、`yaml-cpp/` | Git submodule 目录，当前盘点环境为空 |
| `build/` | 当前为空 |

根 Makefile 先构建 libbpf 和 yaml-cpp，再构建 `tc_prog/` 和 `user_prog/`。BPF 编译链为 `clang -target bpf` 生成 LLVM IR，再由 `llc -march=bpf` 生成 ELF；用户态使用 gcc/g++，链接 libbpf、yaml-cpp、zlib 和 libelf。README 要求 Clang、LLVM、libelf、libpcap、gcc-multilib、build-essential、cmake、Python3，实验环境以 Ubuntu 20.04、Linux 5.14 为例。

当前 `libbpf/`、`yaml-cpp/` 子模块为空，源码目录也没有 Git 元数据，因此不能在当前状态直接完成原工程构建。`.gitmodules` 指向 libbpf 和 yaml-cpp 官方仓库，但本次没有下载或修改外部依赖。

## 2. 四个 TC 程序

四个 section 位于 `tc_prog/tc_prog_kern.c`：

| Section | 原型挂载位置 | 主要行为 |
|---|---|---|
| `tc_init_e` | 节点网卡 egress | 观察正常 overlay 封装包，学习 egress header、远端 PodIP→NodeIP 和 egress ready |
| `tc_masq` | 宿主机 Pod veth ingress | 查缓存后增加 50 字节外层头，修改 UDP 源端口并 redirect 到节点网卡 |
| `tc_restore` | 节点网卡 ingress | 校验外层设备信息，去除 50 字节外层头，改写 MAC 后 redirect 到 Pod veth peer |
| `tc_init_in` | Pod `eth0` ingress | 学习 ingress MAC 和 ingress ready |

`daemon.py` 中的实际加载关系是：节点网卡挂载 `tc_init_e` egress 和 `tc_restore` ingress；Pod `eth0` 挂载 `tc_init_in` ingress；宿主机 veth 挂载 `tc_masq` ingress。

## 3. 原始 Map ABI

Map 全部使用旧式 `struct bpf_elf_map`，设置 `.pinning = PIN_GLOBAL_NS`，其中 `PIN_GLOBAL_NS` 为 2。五个 Map 的源码定义如下：

| Map | 类型 | key | value | 容量 |
|---|---|---|---|---:|
| `ingress_cache` | `LRU_HASH` | `__be32` | `ingressinfo`，16 字节 | 1024 |
| `egressip_cache` | `LRU_HASH` | `__be32` | `__be32` | 4096 |
| `egress_cache` | `LRU_HASH` | `__be32` | `egressinfo`，68 字节 | 1024 |
| `policy_cache` | `LRU_HASH` | `fivetuple`，16 字节 | `action`，4 字节 | 4096 |
| `devmap` | `LRU_HASH` | `int`，4 字节 | `devinfo`，含尾部对齐 | 8 |

源码中的 `devmap` 明确是普通 `LRU_HASH`，不是内核 `DEVMAP`。`devinfo` 没有显式 padding 字段，虽然自然对齐可能使结构体大小为 12 字节，但 v0.5 必须用显式固定 ABI 和 size/offset 测试确认。

共享结构位于 `common/common_defines.h`：

- `fivetuple`：本地/远端 IPv4、端口和协议；
- `egressinfo`：64 字节外层头和 ifindex；
- `action`：两个 16 位 ingress/egress ready 位；
- `devinfo`：IPv4 和 6 字节 MAC；
- `ingressinfo`：ifindex、目的 MAC、源 MAC。

源码没有 `control_map`、ABI version、generation、heartbeat 或 flags。

## 4. 关键硬编码与报文假设

`common_defines.h` 固定 Ethernet=14、IPv4=20、UDP=8、VXLAN=8。解析代码直接按固定 IPv4 头长度取 L4 和内层报文，没有验证 IPv4 IHL、options、分片、VXLAN flags、VNI 或报文长度的一致性。

`is_encap()` 接受 UDP 目的端口 6081、4789、8472，分别覆盖更宽的封装范围，而不是只接受运行期发现的 Flannel VNI/端口。`tc_masq` 和 `tc_restore` 通过 `bpf_skb_adjust_room()` 固定增删 50 字节，使用固定的外层 64 字节缓存。

学习条件是 `(tos & 0xc) == 0xc`。`set_ip_tos()` 清除时使用 `0xf3`，当前效果是清除 `0x04/0x08` 并保留其余位，但 v0.5 仍需改为命名掩码并验证每条失败路径。

源码包含多处逐包 `bpf_printk`。`policy_cache` 使用 `BPF_NOEXIST` 后再直接读改写 value，ingress/egress 并发更新存在 lost update 风险。

## 5. Helper 与 redirect

源码使用了以下主要 helper：Map lookup/update、`bpf_get_hash_recalc`、`bpf_skb_adjust_room`、`bpf_skb_store_bytes`、L3/L4 checksum replace、`bpf_redirect` 和 `bpf_redirect_peer`。

`tc_masq` 当前实际使用标准 `bpf_redirect`；`tc_restore` 当前使用 `bpf_redirect_peer`。`bpf_redirect_rpeer` 只以注释形式出现在 `tc_masq`，没有进入实际调用路径。

`rpeer_kernel_patch` 在 UAPI helper 枚举和 `net/core/filter.c` 中增加 `BPF_FUNC_redirect_rpeer`，实现方式是设置 `BPF_F_RPEER` 后返回 `TC_ACT_REDIRECT`。补丁说明基于 Linux 5.14，并要求特定内核源码和 UAPI 配套，不能视为 v0.5 的必需依赖。

## 6. Pin、TC 和用户态硬编码

原型使用全局目录 `/sys/fs/bpf/tc/globals/`：

- `common_user.h` 将 bpffs 根目录固定为 `/sys/fs/bpf`；
- `set_map.cpp` 将 Map 目录固定为 `/sys/fs/bpf/tc/globals/`；
- `daemon.py` 启动和退出时执行 `rm -rf /sys/fs/bpf/tc/globals/*`；
- v0.5 需要改为 `/sys/fs/bpf/oncache/v1/`，并按对象所有权清理。

TC 加载器通过 shell 调用 `tc`：

- 创建 clsact 前先删除已有 clsact；
- `tc filter add` 不设置固定 priority 或 handle；
- 删除时按方向执行 `tc filter del`，存在删除整组 filter 的风险；
- 设备名、对象路径和 section 名通过 `system()` 拼接执行。

`daemon.py` 还硬编码了 `NODE_IFNAME`、`POD_IFNAME`、containerd socket `/run/containerd/containerd.sock`，只查询 default namespace 的 Running Pod，并依赖 `kubectl`、`crictl`、`nsenter`、`ip`、`grep` 和 `awk`。它没有 Pod UID、resourceVersion、netns inode、所有权文件、删除处理或重启恢复逻辑。

## 7. Overlay 实验耦合

实验脚本主要针对 Antrea，而不是当前 v0.5 的 Flannel VXLAN：

- `scripts/provision.sh` 安装 Antrea v1.10.0；
- `user_prog/set_ovs.sh` 修改 Antrea OVS `br-int` 的 ConntrackState 表；
- OVS 规则把连接状态写入 TOS bit 3，并操作 Antrea register；
- README 的教程和测试结果也以 Antrea 为主。

因此，`set_ovs.sh`、Antrea 规则和 provision 脚本不能直接复用为 v0.5 Flannel Adapter。它们只能作为“原型如何获得 established 标记”的实验参考。v0.5 必须重新实现 Flannel VXLAN 参数发现、规则 compare-and-apply 和健康检查。

## 8. 可复用边界

| 原型内容 | v0.5 处理结论 |
|---|---|
| 四个 TC section 的快速路径角色 | 保留算法角色，按统一 ELF 和新 ABI 改造 |
| 五个 Map 的名称、主要 key/value 语义和容量起点 | 作为 ABI v1 冻结基础，已补充 size/offset/字节序约束 |
| `fivetuple` 方向归一化和学习链路 | 保留语义，修复并发 ready 更新 |
| checksum、adjust-room、redirect 逻辑 | 保留操作意图，补边界校验、失败旁路和计数 |
| 旧 `bpf_elf_map`、全局 pin、TC loader | 不直接复用，改由 Go/cilium-ebpf 和 TC Manager 管理 |
| `daemon.py` | 不作为运行时复用，仅参考原型挂载顺序和 CRI 查询路径 |
| `set_map.cpp` | 不作为控制面复用，改由类型安全的 Map Manager 填充 |
| `set_ovs.sh` 和 Antrea provision | 不复用到 Flannel v0.5 |
| `rpeer_kernel_patch` | 独立实验能力，不能成为 v0.5 必需条件 |

## 9. M0-1 结论

论文源码确认了四个程序、五个 Map 及其原型算法角色，可以作为 M1 数据面迁移的来源。它不是可直接接入 v0.5 的工程实现，必须先完成统一 ABI、`control_map`、显式 pin、严格解析、所有权保护、TC 共存和 Flannel 适配。

本盘点未执行构建、加载、特权 TC 操作或网络修改；源码映射见第 10～14 节，ABI v1 冻结内容以 `docs/02-接口设计.md` 第 6 节为准。

## 14. 映射与 ABI 冻结结论

1. 只复用四个程序和五个 Map 的算法角色，不直接复用原型工程边界。
2. BPF ABI、`control_map`、pin 路径和程序加载方式全部由 v0.5 重新定义。
3. `daemon.py`、shell 脚本和旧 loader 不进入运行时，最多作为迁移和测试参考。
4. Flannel 适配器必须独立实现，不能通过 Antrea/OVS 规则替代。
5. `bpf_redirect_rpeer` 保持可选实验能力，不进入 v0.5 必需条件。
6. BPF ABI v1 的结构布局、Map 定义、`control_map` 和 pin 布局以 `docs/02-接口设计.md` 第 6 节为唯一冻结依据。
7. `devmap` 冻结为普通 `LRU_HASH`：源码通过 key 查出设备信息并由 `tc_restore` 校验，不使用 `bpf_redirect_map`，因此不采用内核 `DEVMAP`。
8. TC priority 固定为 `1000`，四个 handle 固定为 `0x100`、`0x101`、`0x200`、`0x201`；v0.5 首版只支持 `iptables-nft`。
9. M0-7 环境冻结以 `docs/05-开发环境与工具链冻结.md` 为准：宿主机只运行 KVM/libvirt，ONCache 和 Flannel 只运行在两节点 VM 内；Ubuntu 22.04/5.15 为主要兼容基线。

M0-2 验收门：所有论文源码文件已归类为“改造复用、替换、不复用或参考”；每个进入 M1 的源码组件都有来源记录和目标位置；没有把旧 pin、旧 ABI、Antrea 依赖或危险清理逻辑隐式带入 v0.5。

M0-3 验收门：ABI v1 的结构大小、offset、字节序、padding、Map 类型/名称/容量、`control_map` 字段和 pin 目录均已明确；任何不匹配对象不得复用。

M0-5 验收门：`devmap` 类型和访问语义已唯一确定，后续实现不保留普通 Hash 与内核 DEVMAP 两套分支。

M0-6 验收门：TC identity 和 iptables backend 已冻结；外部 priority/handle 冲突不被覆盖，legacy backend 不进入首版支持矩阵。

M0-7 验收门：开发宿主机、两节点 VM、主要兼容基线、源码挂载、工具链、镜像导出和测试 manifest 规则均已明确，环境不依赖宿主机隐式状态。

M0-8 至 M0-12 环境验收门：基础 VM、精确工具链、K3s/Flannel 两节点网络、BPF/TC 能力、宿主机隔离和可重建 manifest 全部通过后，才允许进入 M1。
